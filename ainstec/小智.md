### 将前端网站开放的权限问题

1. 首先需要管理员层面将服务器的开放权限打开。
2. Nginx虚拟主机冲突：在安装Nginx时启动的是默认default配置，这个配置如果不显式ban，那么会将访问默认派发到default，而不是我们自己创建的配置。
	解决方式：使用`curl -I http://127.0.0.1`来查询访问时间戳来比对响应来自哪个模块，确认后移除defalut（取消启动默认配置）。
3. 文件系统权限问题：默认前端是配置在服务器中我的名下，因此我需要将外部访问权限打开。
	解决方式：使用`namei -l`来判断权限定位卡在哪个文职，然后将我的名下加入其他用户权限来穿过校权。

## 素材管理模块（新增）



1. 建表

- 素材表：文件路径、缩略图路径、上传时间、上传人、自增ID。
- 设备下载记录表：记录序列号（id）、设备id（SN）、状态（pending，success，failed）、推送时间、完成时间。



2. 素材存储与处理：

- 上传素材文件

	- 一次最多批量上传20张，并且单个素材限制5MB。
	- 校验文件的魔数来进行安全校验（不只是文件后缀）。

- 生成缩略图：

	- 创造一个RGBA空白图片对象导入导入原图的长宽比（直接修改原图可能会破坏原图，影响后面保存在服务器的原图），然后讲原图嵌入缩略图。

- 采用NearestNeighor，优先采用低开销的缩放算法，牺牲画质换取速度。

	- 当缩略图路径传入数据库失败时，移除所对应的原图防止报错（回滚）。

- 同理，如果数据库写入失败，直接回滚原图和缩略图。



3. 管理后台接口

- 分页查询列表
	- 倒序上传给前端。

- 查询当前用户正在使用的素材。
	- 先查设备id，再查素材id，用来提供批量删除服务。
	- 素材id查询时，直接查询该设备中时间戳最大那个日志，并且排除failed字段

- 批量删除（直接硬删除，即删除数据库和服务器中的数据）
	- 先查询当请用户是否正在使用要删除的素材。
	- 有两个选择
		- 要么取消删除。
		- 如果当前设备正在被使用并且强制删除，那么调取通知设备接口返回给用户。
	- 如果数据库（只存了文件路径）删除成功，但是文件删除失败，那么这里将记录提交给日志而不是回滚数据库。
	- 为了避免二者相反，源码中采用先删除数据库，校验后再删除文件。
- 通知设备：你正在使用的素材已经被删除。

## Bug修改

1. `filepath.Join` 无法阻止 `..` 目录穿越，路径拼接后如果出现`..`会使得恶意跳转到服务器根目录。

  > 1. 使用filepath.Clean和filepath.Join进行两次清洗。
  > 2. 最后使用HasPrefix进行最终绝对路径校验。

2. Redis故障时，由于源码中为数字返回，Redis故障会返回err，因此错误丢弃，返回0，导致暴力枚举限制失效。

  > Redis故障时先返回给前端拒绝登录，做保守处理。

3. Token签发周期：4h，当管理员封禁账号或者删除账号时，Token并不会失效，仍可以保持登录态。

  > 当JWT令牌解析后，后端会去数据库查询用户存在、用户状态。

4. 路由在后端绑定到了engine，导致前端在拼接路由时无法加载缩略图。

  > 把后端路由由engine迁移到了apiGroup。

5. 虽然批量上传定义到了20的阈值，但是Nginx默认只放行1MB的限制。

  > 修改Nginx的放行限制，并将axios前端超时从30s提高到了5min。

### 优化与Bug

> #### 背景
>
> 管理后台批量上传素材，一次20个压缩包，每个包有上百张jpg，后端需要解压，生成icon，生成gif，写文件，入库。

问题一：批量上传时报错*504 Gateway Timeout*

​	一次上传12个无gif报，一分钟左右后报错，但是刷新素材列表，随着时间的推移，不断出现结果。

##### 排查思路

1. Nginx默认超时。

  Nginx的默认超时时间是60s。但是后端仍然在处理，网关先把连接断了。
2. 处理本身是串行的，12个包1min跑不完。

	源码中是一个for循环调用函数处理zip，每个包最重的活是gif生成，时间不够。
	
	**解决方法**：
	
	1. Nginx放宽超时（在服务器中配置）.
	
		```sh
		proxy_read_timeout 300s;
		proxy_send_timeout 300s;
		```
	
		  改完nginx后重新校验：
	
		```sh
		systemctl reload nginx
		```
	
	2. 后端改为并发处理。
	
		sync.WaitGroup+信号量channel控制并发数，结果按下标写入预分配的切片，天然保序，无需加锁：
	
		```go
		type result struct {
		      mat    models.Material
		      errMsg string
		}
		results := make([]result, len(zipFiles))
		sem := make(chan struct{}, 4)  //4个通道
		var wg sync.WaitGroup
		for i, fh := range zipFiles {
		     wg.Add(1)
		      go func(i int, fh *multipart.FileHeader, meta uploadMeta) {
		             defer wg.Done()
		              sem <- struct{}{}
		              defer func() { <-sem }()
		             mat, errMsg := processOneZip(db, fh, meta, uploaderID)
		              results[i] = result{mat: mat, errMsg: errMsg}
		     }(i, fh, metas[i])
		}
		wg.Wait()
		```

3. 并发改完还是超时：SQL写锁陷阱。

	改完后重写测试，依然超时，素材仍然是两个两个冒出来。

	经过排查后发现，原因是藏在事务边界里面，原来的代码把GIF生成放在db.Transaction里面。SQLite是单写库，一个事务持有写锁几十秒，其他进程全在排队等锁结束——并发了个寂寞。

	**解决方法**：重构事务边界+SQLite连接参数。

	把单包处理抽成processOneZip，原则是消耗时间的活放在事务外，事务内则只剩纯DB写入.

4. 结果依然很慢：真正的瓶颈在算法。

	我检查了服务器配置，是2核，并发4、5个包仍然需要4、5min，病根在GIF合成的标准库抖动：

	```go
	draw.FloydSteinberg.Draw(pm, bounds, img, image.Point{})
	```

	GO标准库把图片（原图是26位真彩色）转256色调色板时，每个像素都要对着调色板256次线性查找最近的颜色，如果没找到，还要叠加误差抖动的时间，开销特别大。

	**解决方法**：

	暴力压缩真彩色压缩成15位，对色位进行简化，建立Map缓存，第一帧时间很长，第二帧开始直接map查询，从256次比对改成1次Map查询：

	```go
	pal := palette.Plan9  //256调色板
	// 建立颜色缓存，记录已经匹配过的颜色及其对应的调色板索引，避免重复计算
	cache := make(map[uint16]uint8, 32768) 
	colorIndex := func(c color.Color) uint8 {
	     r, g, b, _ := c.RGBA()
	      key := uint16(r>>11)<<10 | uint16(g>>11)<<5 | uint16(b>>11)
	     if i, ok := cache[key]; ok {
	              return i
	    }
	      i := uint8(pal.Index(c))  //为查到的颜色进行匹配
	    cache[key] = i
	      return i
	}
	
	for y := 0; y < bounds.Dy(); y++ {
	      row := y * pm.Stride
	    for x := 0; x < bounds.Dx(); x++ {
	              pm.Pix[row+x] = colorIndex(img.At(x, y))
	     }
	}
	```

	结果：时间开销降低至2~5s，但是icon图标放大图存在色差（缩小预览图无感）。

> #### 问题二
>
> 测试一个id已存在的素材包，要等很长时间才会报错。

#### 原因：

1. 查重位置太靠后，源码把查重放到了解压+校验所有图之后才查，开销太多。
2. 批量上传接口好似成批返回结果的，要等到接口将包处理完才完整返回JSON。

#### 解决方法：

1. 查重校验移到前面。（极端情况下两个并发请求用同一 id 都过了查重，后到的会被数据库主键约束在 INSERT 时拦住，不会写脏数据）
2. 至于批量上传，想要根治比较困难，成本远大于收益，不管他。

> [!tip]
>
> 1. SQLite或者MySQL做任何并发之前，先检查事务里装了什么。事务只放DB操作，其他的一律扔出去，特别是耗时间的。
> 2. CPU密集任务的并发上线时核数，优化点在降低单任务的成本。
> 3. 标准库不一定完全正确，要根据事实去优化方案。
> 4. 报错一定要快，校验排序要按照时间开销顺序从快到慢。
