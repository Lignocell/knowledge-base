## 关于层级划分

Q: 作为一个新手，我们该从什么地方开始，或者换一个问法，梳理一下项目的结构。
A：
想象在经营一家餐厅，代码分层餐厅来划分。
#### Controller层（前端接待与菜单）

职责：接收客人的请求（HTTP request），校验基本参数（有没有带钱），然后把需求传递给后台，把做好的菜（数据）返回给客人。
重点：开后向外，只负责打交道，不必干活。
#### Service层（后厨主厨）
职责：做菜（业务逻辑）。比如客人点了一道“鱼香肉丝”，大厨要决定先炒肉还是先放酱。它会调用底层的材料（数据库），完成复杂的加工。
重点：所有的计算、判断、事务处理（要么全成，要么全败）都写在这里。
#### Mapper层（仓库管理员）

职责：只负责与数据库打交道，不关心业务。只负责增删改查。你告诉它“给我拿 5 号桌的订单”，它就去数据库里取出来。
重点：它是*离数据库最近*的一层，代码里通常是 SQL 语句。
#### Entity层（原材料）

职责：对应数据库的表，数据库里有一张 user 表，代码里就有一个 User.java 类，字段一模一样。
重点：它是数据库的实体类。
---

在项目中，为了安全和规范，我们不会直接把数据库对象（Entity）直接扔给前端。于是有了各种**DTO/VO**：
1. **DTO (Data Transfer Object)**，	- **用途：** 前端传给后端的数据。比如注册时，前端传过来 UserDTO（含用户名、密码、验证码），但数据库 User 表里不需要验证码字段。2. **VO (View Object)**，	- **用途：** 后端给前端展示的数据。比如用户表里有“密码”字段，但返给前端展示时，我们要用 UserVO 过滤掉密码字段。


### 流水线：

- **前端点餐** -> **Controller** 接收。- **Controller** 交给 **Service** 做饭。- **Service** 交给 **Mapper** 从 **Database** 仓库拿菜。- **Mapper** -> **Entity** -> **Service**。- **Service** 加工出 **VO** 交给 **Controller**。- **Controller** 返回 **VO** 端给前端。
## 正则表达式的拓展

```java
Matcher matcher = Pattern.compile(validPattern).matcher(userAccount);
```

- Matcher

	封装了所有的匹配逻辑，他持有：我写的规则（Pattern）和需要检查的字符串（userAccount）。
- Pattern

	它是正则表达式的入口点，没有公开的构造方法（不能new），必须通过他的静态方法来获取实例。
- comlile

	把这些*字符串*（比如^[a-z]+$）解析并转换成一个*内部的数据结构（模式对象）*。这个过程就像把源代码编译成字节码一样，是为了让后续的匹配速度极快。	执行结束后，我会得到一个Pattern对象。
- matcher

	这一步是将刚才编译好的*“规则”*（Pattern）应用到具体的*“待测目标”*（userAccount）上。它并不会立即开始匹配。它更像*“装弹”*——把“规则”这把枪对准“数据”这个靶子。并返回一个Matcher实例

## 项目亮点

1. 使用BaseResponse来规范化传输前端数据，而不是一股脑的丢给前端。
2. 在定义自定义异常时对构造方法进行了分组，以便于更清晰的调用。
3. 通过“加盐”来提高密码的安全性。
	```java
	String encryptPassword = DigestUtils.md5DigestAsHex((SALT + userPassword).getBytes());
	```

4. 定义了错误码来提高寻找错误的难度。
5. 通过用户脱敏，来防止数据在前端被泄露
