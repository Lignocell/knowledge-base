## Redis 与缓存架构（你的鉴权与防刷底座）

### Q 1：除了 Redis 原生命令，还有哪些方案可以实现分布式锁？⭐⭐⭐⭐⭐
- 基于数据库：
	- 优点：无需额外组件，有 ACID 事务保证。	- 缺点：性能较低，易死锁。	- 使用场景：适用于低性能要求下的场景。- 基于 ZooKeeper，	- 优点：强一致性，临时节点自动释放锁（如果服务器断电，会自动释放锁）。	- 缺点：性能低（比数据库高），部署复杂。	- 使用场景：适用于金融场景。- 基于 Etcd，	- 优点：强一致性，性能好，Lease 机制自动过期。	- 缺点：部署复杂，需 3 节点集群。	- 使用场景：适用于云原生环境。- 基于 Consul，	- 优点：集成服务发现，支持多数据中心。	- 缺点：性能一般。	- 使用场景：适用于多活部署。
### Q 2：对 Redisson 分布式锁了解多少？它的底层机制是什么？⭐⭐⭐⭐⭐
- 原子性问题：Redisson 采用 Lua 脚本，将加锁指令合成一个步骤，防止断电时造成加锁中断，造成死锁。- 锁超时失效问题：大模型调用时间长，如果简单设定过期时间，会发生业务没有跑完锁直接被释放。Redisson 自带看门狗机制，如果开发者没写死过期时间，那么在流程没跑完之前，看门狗会对即将失效的锁进行加时，直到执行完毕。### Q 3：什么是缓存穿透、缓存击穿、缓存雪崩？如何解决？⭐⭐⭐⭐⭐（大厂绝对必考的缓存三连问！）
- 缓存穿透：查询一个不存在的数据，但是 Redis 中没有，每次都得进入数据库查询，造成数据库压力。	- 解决方案，		- 布隆过滤器（must）：它可以在很小的内存空间中快速判断一个元素是否在集合内，会产生误判，但是可以参数调整误判率。		- 缓存空值（must）：我们可以在缓存中存储一个空值，并设置一个较短的过期时间，这样，在短时间内再次查询相同数据时，直接返回空值，
		- 参数校验。- 缓存击穿：是高并发问题，由于热点信息可能会发生缓存过期，那么大量请求会直接去访问数据库。	- 解决方案：可以组合使用		- 避免大量请求同时访问数据库（must）：使用互斥锁，第一个请求获取锁并进入数据库取数据，其他请求返回等待或者返回默认值。		- 热点数据永不过期：我们可以设置定时任务来更新缓存。		- 提前更新缓存:在缓存即将过期时，提前异步更新缓存。- 缓存雪崩：严重系统性问题，特点是大量缓存同时失效，主要发生在服务器重启,缓存数据批量更新等场景下。	- 解决方案，		- 随机过期时间（must）：在批量设置缓存时，在同等设置缓存时间的基础上（比如 30 min），加入 1~5 的随机数。		- 多级缓存，熔断降级，高可用架构等。
### Q 4：Redis 为什么选择单线程做核心处理，却依然那么快？⭐⭐⭐⭐

- Redis 在内存中操作，速度瓶颈在 IO。- 事务中 Lua 需要强一致性，多线程会让实现变得复杂，容易引发并发问题。- 通过 IO 复用进一步提高性能，使用 epoll/kqueue 机制让单线程同时处理多个连接。（epoll 来监视线程是否准备好读取和写入）

### Q 5：Redis 做旁路缓存，如果 MySQL 更新了，此时缓存何去何从？⭐⭐⭐⭐
- 先更新数据库，再删除缓存，并结合过期时间采用兜底机制。
### Q 6：Redis 的5 种基础数据类型是什么？你在项目中用到了哪种？⭐⭐⭐

- String，List，Hash，Set，ZSet（有序集合）。- 高级：Bitmap（位权结构），HyperLogLog（基数统计结构），Geo（地理位置存储和查询），Stream（日志流/消息队列）。- String：具体的使用场景是在*分布式无状态登录鉴权*时。用户登录成功后，我会将用户的敏感信息进行脱敏，并使用 Jackson 将 User 对象序列化为一段JSON 格式的字符串。然后，我利用 Spring Boot 的 `StringRedisTemplate` 的 `opsForValue().set()` 方法，以 `user:login:UUID` 为Key，将这段 JSON 字符串存储进 Redis 的 String 类型中，并设置了 30 分钟的 TTL 过期时间。### Q 7：Redis 的内存淘汰策略有哪些？⭐⭐⭐

- 流派一：躺平策略	- `noeviction`（不驱逐）：Redis 默认的策略。内存满了后，只要是再进来的数据全部报错 OOM。    - _大厂忠告：生产环境绝对不用这个，否则服务器直接宕机瘫痪。_

- 流派二：有底线派（只删加了过期时间的）
	- Redis 会去专门找那些设置了过期时间的数据删除：
	1. `volatile-random`（随机删）：在这批数据中随机删除。	2. `volatile-ttl`（快死的先删）：专门挑那些剩余时间最短的数据删。	3. `volatile-lru`（最久没用的先删）：看下方 LRU 解释。	4. `volatile-lfu`（用的最少的先删）：看下方 LFU 解释。
- 流派三：全部删除
	只要内存不够，只要符合条件都可以删：
	1. `allkeys-random`（全库随机删）：完全看命。	2. `allkeys-lru`（全库最久没用的先删）：大厂最常用的主流策略！
	3. `allkeys-lfu`（全库用的最少的先删）：大厂进阶策略。
- **LRU（Least Recently Used）*
    - **看【时间】*：它是根据“最后一次被访问的*时间**”来淘汰的。    - **举个例子**：数据 A 是三天前被看了一次，数据 B 是五分钟前被看了一次。虽然A 在过去一年里被看了10 万次，但此时此刻，LRU 依然会毫不留情地把A 踢走，保留B，- **LFU（Least Frequently Used）*
    - **看【频率】*：它是根据“被访问的*总次数（热度）*”来淘汰的。    - **举个例子**：同样是上面的数据 A（过去一年看了10 万次）和数据 B（五分钟前看了1 次）。LFU 算法一看：“卧槽，A 是个超级大明星啊！B 只是个偶然路过的透明人。”所以 LFU 会把 B 踢走，死死保留住 A。
