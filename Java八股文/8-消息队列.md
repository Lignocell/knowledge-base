## 消息队列

### Q 1：什么情况下需要使用消息队列？常见应用场景有哪些？⭐⭐⭐⭐⭐
- 异步：在大模型的调用中，需要消耗很长的时间，需要线程在那里等着，引入 RabbitMQ 后我们可以给前端返回稍后查看，提高用户体验。- 削峰：当一时间出现大量请求时，我们需要放入队列中,防止请求过多导致服务器宕机。- 解耦：如果在未来需要添加额外功能时，我们不需要在 ChartController 里去绑定接口，只需要在 Exchange 中配置即可。
### Q 2：如何保证 RabbitMQ 的消息不丢失？⭐⭐⭐⭐⭐

- 无非是从生产阶段、存储阶段、消费阶段动手脚、- 生产阶段要有重试和确认机制。只要消息没有到达队列，MQ 会调用 Publisher Confirm 和Return Callback 机制在代码中做重试。- 存储阶段在底层配置 durable（包括 Exchange 和 Queue），设置为true，保证消息同时刻在磁盘上，断电后自动回复。- 消费阶段是从关闭自动确认改为 Manual ACK。废弃Spring 默认的自动确认机制，改为当数据库更新后，调用 basicNack()，如果中间发生异常，配合死信队列将脏数据隔离，留作后续重试。
### Q 3：如何保证消息不被重复消费？⭐⭐⭐⭐⭐
- 消息重复消费是不可避免的，关键是保证消费的幂等性。- Redis Set 存储消息 ID，原子检查是否存在（Set 的不可重复性）。- MySQL 唯一索引，重复插入触发约束报错。- 在我的项目中，我可以尝试在调用 AI 接口之前，先去数据库查询状态，如果为成功或者失败，那么我们直接让MQ把消息删掉。
### Q 4：RabbitMQ 常见的四种交换机模式是什么？有什么区别？⭐⭐⭐⭐

- Direct(直连模式)：消息的路由键需要和队列匹配才允许被分配。- Fanout(扇出模式)：全服大喇叭，他会把消息复制并传递给所有链接他的队列。- Topic（主题模式）：它的路由键全部是特殊的命名格式比如 `user.login.success`）。队列在绑定交换机时，可以设一个*通配符*暗号（比如 `user.*.success` 或者 `user.#`）。    - `*` 只能代替一个词。    - `#` 可以代替零个或多个词。- 只要消息的路由键与*模糊匹配**上队列的暗号，就扔进那个队列。- Headers(头模式)：被淘汰了，不用看。
### Q 5：MQ 消息积压了怎么办？⭐⭐⭐
- 紧急止损->根源排查-->长期优化。- 紧急止损：先暂时增加消费者快速处理积压的队列。- 根源排查：先消费者，消费者消费速度不足，或者处理逻辑冗余等等；然后是生产者，最后再排查其他问题。- 长期优化：异步化处理或者批量处理等等。### Q 6：如果消费者消费失败了，一直无限重试怎么办？（死信队列 DLX 的概念）⭐⭐⭐
- 可以配置一个死信队列，待报出异常后被捕获，并进入死信队列中，然后定义具体的处理方法。
